## Current Documentation Maintenance Rules

This section is the **sole canonical maintenance contract** for Rotom Project Documentation. `01-Rotom-Server-Inventory.md` defines RPD membership and the source map; other RPD files may point here, but they should not duplicate this procedure.

Update this log as part of the same task whenever a substantive change is made to any Rotom Project Documentation file. This includes documented configuration changes, corrected findings, new verification results, adopted decisions, proposed architecture, methodology changes, and plans that are completed or withdrawn. A documentation-only update still belongs here; it does not mean the server was changed.

Do not add an entry for an unchanged re-upload, download, repackaging, or a formatting-only edit. Record typo corrections only when they change the meaning of a command, path, ID, or other operational detail. Discussion alone does not require an entry until a decision or finding is incorporated into the documentation.

The sole canonical documentation-update command is **`Update the RPD`**. It means apply this maintenance procedure to **the final supported state established in the current chat**. It authorizes documentation preparation and packaging only; it does **not** authorize changes to Rotom, Proxmox, Docker, NAS, networking, applications, external services, or other live state unless those changes are separately authorized.

The canonical active-ticket command is **`Work on ticket JAR-*`**, replacing `JAR-*` with the exact Linear ticket identifier. It authorizes Codex to work autonomously within that ticket's verified scope and acceptance criteria until it is complete, verified, documented, and ready to close. Before changing live state, Codex must read the ticket and relevant current RPD, inspect the live state, and compare observed and documented state. It must make reasonable routine implementation decisions within the ticket scope, use the smallest safe change, and keep Linear current with meaningful verified milestones, material scope/design decisions, blockers, rollbacks, and intentional deferrals. Linear updates must not be a raw command transcript or duplicate routine diagnostics.

An intermediate failure, partial progress, unresolved acceptance criterion, or failed verification is not a completion or handoff condition. Codex must investigate the evidence and continue with the next safe, scoped approach. Codex must not declare the ticket complete merely because an intermediate step failed or more work remains. It must request Jared's input before a destructive action; obtaining, creating, changing, or exposing a secret or credential; modifying protected backup/recovery behavior or data; or acting on a genuine ambiguity that cannot be safely resolved from available evidence. An unavoidable access or evidence blocker must also be reported rather than bypassed. PVE remains Jared-executed: when a PVE check or change is required, Codex supplies the established ticket-specific preflight/action/verification blocks and waits for Jared's output before proceeding where that evidence is required.

Before reporting a ticket ready to close, Codex must satisfy its acceptance criteria (or record Jared's explicit waiver), complete final appropriate live-state verification, record the meaningful final outcome in Linear, and update the RPD from the final supported state under this maintenance contract. “Ready to close” does not itself authorize closing the Linear ticket.

For each `Update the RPD` task:

1. Review the current chat and the complete current Available Sources set. Available Sources remains the membership boundary for Rotom Project Documentation, regardless of filename, extension, format, document type, or purpose.
2. Establish the **final supported state** from the chat. Include verified changes, explicit decisions, meaningful corrections, clearly labeled proposals, and unresolved findings worth preserving. Do not promote superseded ideas, abandoned approaches, failed experiments, suggested-but-unrun commands, or temporary troubleshooting states unless they have lasting historical, recovery, or diagnostic value.
3. Update every materially affected RPD file while preserving still-valid information, evidence provenance, and the distinctions between **Current**, **Historical**, **Retired**, **Proposed**, and **Needs Verification**. Leave unaffected files unchanged.
4. Cross-check the complete current RPD for contradictions introduced or exposed by the update. Reconcile contradictions where the available evidence supports a resolution; otherwise preserve the uncertainty explicitly rather than guessing.
5. Add one dated entry at the top of **Change History**, below this maintenance guide, for the documentation task. Use `YYYY-MM-DD` in Rotom's project timezone, `America/Los_Angeles`. State the actual change or evidence date separately if it differs from the documentation date. Combine related work from the same task into one entry.
6. In that entry, list the changed filenames and briefly explain what changed and why. Label relevant items **Implemented**, **Documentation only**, **Proposed**, or **Verified**. Use **Verified** only for results supported by supplied output or an actual check, identify the evidence, and record unresolved checks or limitations. Keep passwords, tokens, keys, and other secrets out of the log.
7. Preserve earlier dated entries as historical evidence. Do not silently rewrite history to match current terminology or policy. If an older entry is wrong, add a dated correction identifying what it supersedes. Historical references to superseded RPD update commands remain historical rather than current instructions.
8. Complete RPD delivery according to the execution environment:
   - **ChatGPT on Mac (non-Codex):** deliver replacement copies of the **materially changed RPD files individually** and package the **complete current RPD set**, including unchanged members, into one ZIP named **`Rotom-Project-Documentation-YYYY-MM-DD.zip`** using the documentation-update date in `America/Los_Angeles`. Tell Jared to run `rpd path` on the Mac to resolve the active local checkout, copy the materially changed files into that checkout, manually replace the corresponding Available Sources copies, then run `rpd commit "<relevant concise commit message>"`, `rpd check`, and `rpd push` on the Mac and verify success. ChatGPT prepares the files and instructions only; it does not execute the RPD Git commit or push itself.
   - **Codex on Mac:** resolve the active local RPD checkout with `rpd path` and work directly in that checkout. After the final RPD files are complete, run `rpd commit "<relevant concise commit message>"`, then `rpd check`, then `rpd push`, and verify the commit and push succeeded. A separate replacement-file/ZIP package is not required unless Jared explicitly requests one.
   - **Codex on Rotom:** resolve the active local RPD checkout with `rpd path` and work directly in that checkout. After the final RPD files are complete, run `rpd commit "<relevant concise commit message>"`, then `rpd check`, then `rpd push`, and verify the commit and push succeeded. A separate replacement-file/ZIP package is not required unless Jared explicitly requests one.
   - **All environments:** Available Sources replacement remains manual by Jared. Do not open or control a browser for synchronization, claim a manual destination is updated before Jared confirms it, commit unrelated changes or temporary files, or commit secrets. If an `rpd` check, commit, or push fails, stop and report the problem rather than bypassing the guardrails. Preserve existing RPD filenames whenever possible and do not add checksum manifests, packaging metadata, generated README files, or other non-RPD extras unless explicitly requested. Generated packages and separate artifacts belong under `Downloads/`; the local `sources/` mirror remains read-only.
9. For Rotom work tied to an active Linear ticket, keep that ticket current as meaningful work is verified: record material design or scope decisions, verified implementation milestones, blockers, rollbacks, and intentional deferrals as they occur. Do not use Linear as a raw command transcript or duplicate routine diagnostic output. When ChatGPT is actively assisting with the ticket and Linear access is available, these meaningful updates should be made during the work without requiring Jared to separately request each one. The RPD remains the canonical verified as-built source of truth; update it from the final verified state at ticket closeout.


Keep future entries brief: the change log should point to the detailed documents rather than duplicate them. Updating the log for a task does not require a second entry merely to record that log update.
